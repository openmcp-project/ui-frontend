# Fix: MCP wizards on ProjectPage lose state / reopen / disable Next

## Context

On the Project page, the "Create Managed Control Plane" wizards (V1
`CreateManagedControlPlaneWizardContainer`, V2 `CreateControlPlaneV2WizardContainer`)
— and the corresponding **edit** wizards launched from a control-plane card —
intermittently reset their in-progress state, close/reopen, or have the **Next**
button unexpectedly disabled. The user experiences this as "something triggers a
refetch that resets the wizard."

The root cause is **not** a single bug but a fragile architecture: the wizards are
mounted deep inside a subtree that is continuously re-rendered and occasionally
**remounted** by two independent Apollo GraphQL-subscription refetch layers, and the
whole page (or card) is torn down whenever a refetch transiently errors. Because
wizard open-state and form state are local component state, any remount destroys them.

Intended outcome: the wizard lifetime is decoupled from list refetches so a user can
fill in a multi-step wizard uninterrupted, regardless of background data churn.

### How the pieces fit today

```
ProjectPage ── useWorkspacesQuery (Apollo useQuery + useSubscription → refetch on every WS event, 300ms debounce)
  └ ObjectPage
     └ ObjectPageSection#workspaces
        └ ControlPlaneListAllWorkspaces        (stable key per workspace)
           └ ControlPlaneListWorkspaceGridTile (LOCAL open-state; wizards mounted here)
              ├ useMcpsQuery (useQuery×2 + useSubscription×2 → refetch on every MCP/CP event)
              ├ [create open?] CreateManagedControlPlaneWizardContainer  (V1)
              ├ [create open?] CreateControlPlaneV2WizardContainer       (V2)
              └ ControlPlaneCard
                   └ EditManagedControlPlaneWizardDataLoader / EditControlPlaneV2WizardDataLoader
                     (edit wizards; open-state LOCAL to the card)
```

### Confirmed root causes (file:line)

1. **Whole-page unmount on transient refetch error.** `ProjectPage.tsx:120`
   `if (error || !workspaces || !projectName)` renders a full-page error, unmounting
   the entire subtree (incl. any open wizard) on *any* Apollo `error` — including a
   transient refetch error while previous data is still present. (`isPending` at
   `:105` is already correctly initial-load-only; the error branch is not.)
2. **Wizard lifetime tied to a remountable tile/card.** Open-state is local
   `useState` in `ControlPlaneListWorkspaceGridTile.tsx:59-61` (create) and in
   `ControlPlaneCard` (edit, mounted at `ControlPlaneCard.tsx:330-351`). Keys are
   stable, so *ordinary* re-renders preserve state — but a workspace transiently
   dropping from the refetched list (Zod parse failure `useWorkspacesQuery.ts:77-84`,
   dedup, or transient error) remounts the tile/card and destroys wizard state.
3. **Self-triggered refetch cascade.** The wizard's own create/update mutation emits
   workspace + MCP SSE events, which `useWorkspacesQuery.ts:60-72` and
   `useMcpsQuery.ts:258-284` turn into debounced `refetch()`s that re-render the
   wizard's ancestors.
4. **Re-render amplifier.** `AuthContextOnboarding.tsx:183` provides an **unmemoized**
   value object; the token-refresh timer (`:131-146`) calls `setUser(new object)`
   periodically, re-rendering every consumer including open wizards.
5. **Edit-mode "Next disabled".** V2 KPI hooks (`spaces/controlPlaneV2/components/Kpi/use*Query.ts`)
   return raw `isLoading: queryResult.loading` with `notifyOnNetworkStatusChange:true`.
   Service mutations fire `refetchQueries:['GetCrossplane']` etc., re-flipping `loading`
   true → `isKpiLoading` (`CreateControlPlaneV2WizardContainer.tsx:314-322`) re-disables
   Next (`:903`) and blocks `onNextClick` (`:713`).
6. **State-clobbering prefill effects.** Effects keyed on `isOpen`/`initialData`
   re-run `reset()`/`setValue()` on remount and on new `initialData` identity:
   V2 `:273-282`, `:796-812`; V1 `:233-240`, `:437-464`; and V1 componentsList prefill
   `useComponentsSelectionData.ts:216-226` (unguarded — a refetched `initialData`
   identity change wipes the user's version edits).
7. **Transient-invalid window (latent).** The template/charging effect
   (V2 `:231-247`, V1 `:189-205`) does two separate `setValue(...,{shouldValidate:true})`
   calls then remounts `MetadataForm` via `metadataFormKey` on every metadata visit —
   a brief `isValid=false` frame. Latent today (`templates` is `[]`) but the
   `MetadataForm` remount already runs needlessly.
